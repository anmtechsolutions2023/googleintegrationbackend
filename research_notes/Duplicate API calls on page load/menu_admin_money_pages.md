# Duplicate / avoidable API calls on page load: Menu, Money, Guests, Insights, Admin/Org, Outlet, Setup

Code audit of `/Users/animeshmalhotra/DATA/projects/googleintegrationfrontend/tenant-auth-ui/src` (paths below are relative to `src/`). Billing/Kitchen/tables/orders/QR/cash screens were left out. "Confirmed" means the code path was read end to end. "Suspected" means it depends on runtime data or on how users behave.

General context: `index.js:9` wraps the app in `<React.StrictMode>`, so in **development only** every mount effect runs twice. All counts below are for production. There is **no shared cache** for reference lists such as branches, categories or tax groups. Each screen calls `posService.getPosBranches()` (GET `/api/pos/branches`, `services/posService.js:388`) on its own, at 20 or more call sites. Only two things are memoised at module level: the export catalogue (`services/exportService.js:43`, GET `/api/exports`) and dish photos (`utils/dishPhoto.js:81`).

## Which pages fetch the same reference list more than once on load?

### Takeaway
On first load, few pages request the *same URL twice*. The confirmed same-endpoint duplicates are: AuditLogs (GET `/api/audit-logs` twice), GenericCrudPage modules that reference both `costInfos` and `taxGroups` (taxGroups twice), Access & Staff › Roles (roles list twice, then a full remount loop), and CostInfoDrawer (mappers twice). The bigger cost is pages that re-download every reference list again after an unrelated state change, such as a pagination click, a save or a keystroke.

### Cited Findings
- **AuditLogs (Org › Audit)**, confirmed, medium. `pages/AuditLogs.js:106-118` sends GET audit logs `{page:1, limit:500}` on mount only to fill the Email/Action dropdowns. `pages/AuditLogs.js:121-123` then sends the paged `fetchLogs()` call to the same endpoint. That is 2 requests on load, and one of them is a 500-row audit scan. A third call goes to `getAuditCategories()` at line 99. The dropdown options should come from a distinct-values endpoint.
- **GenericCrudPage: taxGroups fetched twice**, confirmed, low to medium. `fetchReferenceData` (`components/MasterData/GenericCrudPage.js:383-427`) fetches each referenced module once (it uses a Set, so there is no per-field duplication). If `costInfos` is a reference, though, `buildCostInfoLabels` (`GenericCrudPage.js:121-124`) makes another GET for `taxGroups` (`/api/...taxgroups?page=1&limit=MAX_LIMIT`). For `itemDetails` (references: categories, uom, costInfos; `config/modules.js` around lines 850-866) and `batchDetails` (costInfos, uom, mapProviderLocationMappers, branchDetails; around lines 764-785), opening the page costs the list plus 3-4 reference lists plus 1 extra taxGroups call. Any module that references both costInfos and taxGroups gets taxGroups twice.
- **Access & Staff › Roles tab**, confirmed, medium. `pages/frontdesk/AccessControl.js:72-90` loads `adminService.listRoles()`, `getPosBranches()` and `listFeatures()`. `RolesPanel` (`components/frontdesk/RolesPanel.js:141-153`) calls `listRoles()` again plus `listRolePermissionMatrix()`, so the roles list is fetched twice when the tab opens. `RolesPanel` also receives `onRolesChanged={load}` (`AccessControl.js:136-140`). The parent's `load` sets `loading=true`, which unmounts RolesPanel and remounts it after the reload. Every role save or delete therefore costs parent (3) + RolesPanel (2) = 5 requests, roles twice and branches/features again.
- **AccessSummary drawer**, confirmed, low. `components/frontdesk/access/AccessSummary.js:33-48` sends `listRolePermissionMatrix()` again, although RolesPanel and the parent already hold role data. It also sends GET audit logs `{category:'USER_MGMT', limit:200}` and filters to one phone number on the client. That is 2 requests each time a person's summary opens, one of them a 200-row scan to show at most 8 rows.
- **CostInfoDrawer**, confirmed, low. `components/MasterData/CostInfoDrawer.js:42-66`: when the drawer opens it requests `getTaxGroups`, `getTaxTypes` and `getMappers`. For an existing Cost Info it then sets `taxGroupId`, which triggers `refreshGroup` (lines 74-90): `getTaxGroupRate` plus a second `getMappers()`. That is 6 requests per open, with mappers fetched twice.
- **Dues › Written off**, confirmed, low. `pages/frontdesk/Dues.js:95-106` sends `getWriteOffs(thisMonthRange())` for the header count. Switching to the "Written off" view mounts `WriteOffRegister` (`components/frontdesk/WriteOffRegister.js:30,57`), which defaults to `period='month'` and calls `getWriteOffs` with the same range, plus its own `getPosBranches()` (line 43). The same month's write-offs are fetched twice.
- **Finance (Money › Overview / GST)**, confirmed, low to medium. `pages/frontdesk/Finance.js:181-193` fetches branches, `getFloors({limit:MAX_LIMIT})` and `getTables({limit:MAX_LIMIT})` on every mount, whichever tab is open. The floors and tables lists only feed the filter bar (`Finance.js:243-245`). `money.overview` and `money.gst` both mount `<Finance>` (`config/workspaceScreens.js:101,110`), so moving between them re-fetches all three. Each load is 1 report + 3 lookups. The Products and Customers tabs each fire 2 report requests by design (`Finance.js:90-117`); that is documented and not a bug.
- **Cross-screen branch list**, confirmed, low each. GET `/api/pos/branches` is called independently by Finance:188, Expenses:104, Campaigns:72, CampaignDetail:81, PaymentMethods:27, PosSettings:69, ReceiptFormat:127, DailyStock:128, Assets:86, Portals:91, AccessControl:77, WriteOffRegister:43, ImportDrawer:64, ExportDialog:66, ReportsBundleButton:34 and `hooks/usePosBranch.js:42` (BusinessProfile). It is also requested through `crudService.getReferenceData('posBranches')` by PosCrudPage modules (`config/posModules.js:63,108,165`, MenuMaster:60). There is no cache, so each navigation re-requests it. ExportDialog and ReportsBundleButton request it again every time the dialog opens, after the host page already has it.
- **Export buttons**, checked, no issue. `hooks/useExports.js` uses the module-level promise cache in `exportService.getExports`. Many ExportButtons on one page share one GET `/api/exports`.

## Any N+1 patterns (per-row fetch)? Estimate for a 467-dish menu

### Takeaway
There is one real per-row pattern: dish photo thumbnails on Menu › Dishes, one authenticated blob GET per dish. It is lazy and cached in memory, but scrolling the whole 467-dish list fires up to about 467 requests. That cache is lost on a full reload, and the browser HTTP cache cannot help because the requests go through axios as blobs. No other per-row detail or name-lookup calls were found. Reference lookups load whole lists once.

### Cited Findings
- **Dishes list photos**, confirmed, medium to high on large menus. `pages/frontdesk/Dishes.js:332` renders `<DishPhoto>` for each row. `components/DishPhoto.js:20-36` uses an IntersectionObserver (rootMargin 200px) and calls `staffPhotoUrl` (`utils/dishPhoto.js:81-95`), which sends GET `/api/menu/photos/:itemId?size=thumb&v=<version>` with `responseType:'blob'`. The list is not paginated. On first paint only the visible rows load, roughly 15-30 plus the 200px margin. A full scroll, or Ctrl+F or select-all in a tall window, fires up to 467 requests, one per dish with a photo. The cache is keyed by `itemId:version:size`, so SPA navigation does not re-download, but a browser reload does, and nothing goes through the HTTP cache. A sprite or batch thumbnail endpoint, or a public cacheable URL with `Cache-Control: immutable` keyed on version, would remove most of this.
- **Dishes: full reload after each row action**, confirmed, medium. `Dishes.js:94,117,139` call `await load()` (GET `menuService.listDishes()`, the whole 467-dish menu) after a single-row photo upload, a bulk tag/portal/channel action and a clear. One photo upload costs 1 PUT plus a refetch of all 467 dishes. Thumbnails do not re-download unless that dish's version changed, thanks to the cache.
- **BusinessProfile branding previews**, confirmed, medium (large payloads). `pages/frontdesk/BusinessProfile.js:199-210` fetches `getBranchMedia(branchId, kind)` once per present kind (logo, paymentQr). These are data URIs, possibly hundreds of KB to MB. The effect depends on the whole `profile` object, so **every text-field save** (`save()` at line 163 replaces `profile`) downloads both images again. After `putMedia`/`removeMedia`, `load()` refetches the profile and then both images, including the unchanged one. Per save that is 2 avoidable image GETs.
- **MenuMaster (Menu › Items)**, confirmed, medium. `pages/frontdesk/MenuMaster.js` uses `PosCrudPage`. On mount it requests GET `/api/pos/item-meta` (all rows, `components/frontdesk/PosCrudPage.js:129-141`) and, through `PosCrudPage.js:159-177`, **eagerly** requests 8+ reference lists at MAX_LIMIT: itemDetails (about 467 rows, effectively the same dish set again), posFoodType, posMeatTypes, posBranches, posChannel, posVariant, posAddonGroups and posMenuTags (MenuMaster.js:31-94). These lists are deduplicated (each requested once) but only used inside the edit modal. Load is about 9-10 requests, two of them about 467 rows each. Bulk field edits then `api.refresh()` (MenuMaster.js:370) the full item-meta list rather than patching rows (the Active toggle does patch locally, lines 249-262).
- **Feedback page**, suspected, medium as the CRM grows. The `posCustomers` reference (`config/posModules.js:161`) makes `PosCrudPage` load the **entire customer list** at MAX_LIMIT just to fill a select.
- **ReceiptFormat preview**, confirmed, low. `pages/frontdesk/ReceiptFormat.js:154-172` sends GET ledger documents `{limit:1}` and then GET ledger document `/:id` for a sample bill: 2 sequential calls per branch change, which is intentional.
- **CampaignDetail**, confirmed, low to medium. `pages/frontdesk/CampaignDetail.js:80-84` loads branches, **all itemDetails (about 467)** and all categories on mount, only for the offer editor.

## Any effects that refetch on every render or on unrelated state changes?

### Takeaway
No effect refetches on every render; all deps are stable `useCallback`s or primitives. The worst unrelated-change refetches are three. Ledger search is not debounced: 2 requests per keystroke, one of them the unrelated dues summary. GenericCrudPage refetches every reference list on each pagination change. Portals and AccessControl reload their reference data after every action.

### Cited Findings
- **Ledger search not debounced**, confirmed, high (DB load on typing). `pages/frontdesk/Ledger.js:113-138`: `load` depends on `search`, and the input calls `setSearch` on each keystroke (`Ledger.js:292`) with no debounce. Each keystroke fires GET ledger documents `{limit:100, search}` **and** `posService.getDues()` (lines 132-135). The dues banner does not depend on the filters at all. Typing a 10-character invoice number sends about 20 requests, 10 of them dues aggregations that cannot change. Changing status, docType, dates or the dues toggle also refetches dues. By contrast, Dues.js:89-92 debounces search by 250 ms.
- **GenericCrudPage: reference lists refetched on pagination**, confirmed, medium. `components/MasterData/GenericCrudPage.js:464-469` runs `fetchData()` **and** `fetchReferenceData()` in one effect whose deps include `fetchData`. `fetchData` depends on `pagination.page` and `pagination.pageSize` (line 324). Every page or page-size change therefore re-downloads all reference modules at MAX_LIMIT. For itemDetails that is categories, uom, costInfos and taxGroups: 4 lists per page click. Split the effect so references load only on `[referenceModules]`. The same file refetches the full list after create, update or delete (lines 582, 675).
- **PosCrudPage refetch after save/delete**, confirmed, low. `components/frontdesk/PosCrudPage.js:336,352` call `fetchData()` (full list at MAX_LIMIT) after each save or delete, even though `patchRows` (line 153) exists for local updates.
- **Portals reload after each action**, confirmed, low. `pages/frontdesk/Portals.js:86-100`: `load()` re-requests portals, **branches and payment modes** together, so every portal, credential or branch-form action re-downloads the two static lookup lists.
- **AccessControl Refresh / onRolesChanged**, confirmed, medium. See the remount loop above: `loading` toggling unmounts the active panel, so its own fetch runs again (users, invitations, roles plus matrix, or tenants).
- **ExportDialog preview**, checked, OK. `components/export/ExportDialog.js:81-95` re-previews on every params change, debounced by 300 ms; `screenFilters` is memoised (line 40). There is no render loop.
- **usePrintReceipt in Ledger**, checked, OK on load. `components/frontdesk/receipt/usePrintReceipt.js:91-116` only fetches once a document with a BranchId is selected. After that it re-requests the receipt format on every window `focus` and on a TTL interval for as long as the drawer is open. That is intentional but chatty.
- **StrictMode**, confirmed, dev only. In development every mount fetch listed here runs twice (`index.js:9`). Do not count these when you profile production.
