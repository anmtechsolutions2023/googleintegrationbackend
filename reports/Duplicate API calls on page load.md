# Till actions and keystrokes multiply database work

The worst repeated API traffic in Restro OS does not come from the first paint of a page. It comes from what pages do after they load. On the till (`/billing`), **every cart change sends an undebounced pricing quote, and then a second identical quote** once the offers preview lands. **Every till action (create order, fire KOT, transfer, settle, delete) re-runs a full `load()` of 10+ lists plus every item-meta page.** On Money › Ledger, **each keystroke in search sends 2 requests**, one of them a dues aggregation that cannot change. The kitchen display re-pulls 3 full lists every 15 s. One true same-page duplicate shows up in production: `GET /api/pos/qr/orders/pending` is polled twice in parallel on `/billing` and on the QR inbox. The backend turns each of these calls into more work than it looks like. A cold `liveAccess` cache costs **3 sequential auth queries**, about 61 audited modules write **an audit `INSERT` on every GET**, and the DB pool defaults to **4 connections**. One that a single Finance overview request can use up entirely. A typical audited list GET costs **6-10 queries** on a cold instance, and every duplicate repeats all of them, audit row included. The frontend has no request cache or de-duplication beyond the exports catalogue, no `AbortController`, and no pausing of pollers in background tabs. This is a findings list only. No code was changed.

All frontend paths are relative to `googleintegrationfrontend/tenant-auth-ui/src` and backend paths to `googleintegrationbackend/src`. Every finding comes from reading the code (static audit). Nothing was run or measured. "Confirmed" means the code path is unambiguous. "Suspected" means the outcome depends on runtime data or user behaviour. Call counts are for the **production build**. Development doubling is covered separately below.

## The till is the hot path: quotes and reloads dominate

Billing is the screen that stays open all shift, so its costs add up. On mount it sends about **13 GETs plus N menu pages**. That is acceptable once. The trouble is that the same `load()` runs **after every till action** (`Billing.js:1474` through `:3432`). A busy service with a few hundred actions per terminal therefore re-downloads the whole menu, variants, addons and payment modes hundreds of times. Each item-meta page alone costs about **5-6 queries, an audit `INSERT`, and 2 concurrent pool connections** during pricing. The fix direction is to re-fetch only orders, KOTs and tables after an action.

The quote cascade is subtler. The quote effect depends on `[cartItems, effectiveCartDiscounts]` with no debounce (`Billing.js:756-796`). The debounced (350 ms) offers preview then always produces a new `cartOffers` object, and `effectiveCartDiscounts` is rebuilt as a new object every time (`:745-749`). So the same cart is quoted again **even when no offer applies**. Requests that the client discards as stale still reach the server and do the full pricing work. The settle modal repeats this pattern on a smaller scale. Debouncing the quote and memoising `effectiveCartDiscounts` by value would remove most of it.

On top of this, the QR pending poll runs twice: once in Billing's own 15 s poller and once in the `qrAlert` banner the workspace config attaches to `/billing`. That gives **about 8 requests a minute per open till** instead of 4. The QR inbox (`QrOrders.js`) has the same problem, because `QrOrderAlert` runs its effect before its `return null`. The Floor › Tables page, where only the banner polls, is fine.

## Money, menu and admin screens waste work on interactions

Outside the till, the worst case is **Ledger search**. Each keystroke sends a 100-row document search plus `getDues()` (`Ledger.js:132-135`). Dues.js already debounces its search by 250 ms (`Dues.js:89-92`), so the pattern to copy already exists. GenericCrudPage puts `fetchReferenceData()` in the effect keyed on `fetchData`. Every pagination click on itemDetails therefore re-downloads categories, uom, costInfos and taxGroups at MAX_LIMIT, and each of those is an audited list. Menu › Dishes is the one real per-row pattern. It sends up to one thumbnail request per dish while scrolling. Thumbnails are fetched as axios blobs, so they skip the HTTP cache and come back on every browser reload. Serving them from a versioned URL with `Cache-Control: immutable`, or from a batch thumbnail endpoint, would remove most of these requests. On load, the true same-endpoint duplicates are AuditLogs (a 500-row scan just for dropdown values), Roles (`listRoles` fetched by both parent and child, plus a remount loop on every change), taxGroups on costInfo-referencing modules, Dues' write-off range, and CostInfoDrawer's mappers.

## Backend multipliers turn each extra call into 6-10 queries

Three server-side behaviours make each extra frontend call more expensive.

**Audited GETs.** `auditLogCrud` maps every GET to "Viewed X list/details" and always calls `writeAuditLog`, one `db.execute(AUDIT_LOGS.INSERT_MIDDLEWARE)` on `res.finish` (`middleware/auditLogger.js:17-21, 77-112`). The plain `auditLog` works the same way. Neither skips GETs or filters out DEBUG level. About **61 modules** use it. The most frequent are `GET /api/pos/branches` (`posbranch.routes.js:21-28`, whose own comment says every branch-picker screen reads it), `/api/pos/settings` (`possetting.routes.js:28-29`), item-meta list and detail (`positemmeta.routes.js:14, 25-30`), orders, KOT-adjacent lists, cash sessions, and the polled online-order queue (`posonlineorder.routes.js:32`, which writes an audit row on every 10 s poll from `useOrderQueue.js:18,127`). Every polled or duplicated read therefore also writes a row and grows the audit table. These reads are not audited: `/api/exports`, `/api/menu/*`, tax settings, business profile, and the ledger overview report.

**liveAccess cache misses.** `authenticateToken` calls `liveAccess.refresh` for every tenant member (`middleware/authMiddleware.js:23-58`). On a miss it runs **3 sequential queries**: access flags, all grants, and role names (`liveAccess.js:57`, `modules/auth/access.js:25, 41-46, 58`). The cache is an in-process Map with a **15 s TTL** and 5000 entries, cleared wholesale when full (`liveAccess.js:31-38, 67-76`). On Vercel serverless, where instances are cold and run in parallel, misses are common. There is also no in-flight promise memoisation, so **N concurrent requests from one user on a cold key run 3N queries**. Billing's 13-call burst can therefore cost up to 39 auth queries. `checkScope` itself costs no queries. Tests will not show any of this, because the cache is disabled under `NODE_ENV=test` unless `LIVE_ACCESS_IN_TESTS=1` (`liveAccess.js:43-44`).

**Connection fan-out.** The pool defaults to **`CONNECTION_LIMIT` 4, `MAX_IDLE` 1** (`config/config.js:32-33`). `priceCostInfos` runs `Promise.all([getChainForCostInfos, isGstCharging])` as two separate pool calls (`pricing.service.js:33-37, 55-58, 122`). `attachAvailability` does the same for schedule and timezone (`positemmeta.service.js:363`). `overviewReport` runs its sales, expense, cash-flow and write-off reports on four parallel `withConnection` calls (`ledger.report.service.js:447-452`), which is **the whole pool for one request**. These calls don't deadlock, because nothing is nested, but they serialise everything else behind them. `withConnection` already accepts an existing connection (`utils/dbHelper.js:21-37`), but these callers don't pass one. Putting this together, a typical audited list GET with a cold cache costs **3 auth + 2-6 data + 1 audit ≈ 6-10 queries**, and the server de-duplicates nothing.

## Development-only StrictMode doubling

`index.js:8-12` wraps the app in `<React.StrictMode>`. In development every mount effect runs mount → cleanup → mount, so **every fetch-on-mount above appears twice in the dev Network tab**. For example, the QR pending pair shows 4 requests on load instead of 2. The cleanup flags (`alive`, `live`, `cancelled`) only block stale state updates. They do not cancel the HTTP request, because no `AbortController` is used, so the backend really does receive both. This does not happen in the production build, so leave these extra calls out when you profile. The `/api/exports` catalogue is the exception. It stays at 1 even in dev, because the second mount reuses its cached promise.

## Checked and found fine

The global shell makes no requests on mount. `AuthProvider` only decodes the cookie (`context/AuthContext.js:21-32`). `FrontDeskProvider` defines refresh helpers but has no effect and no callers (`context/FrontDeskContext.js:9-79`). It is dead code, but if it is ever wired up next to Billing's own load it would double six lists. Navbar, Guards, WorkspaceLayout/Rail/Header/Redirects, SectionedTab, BrandMark and `OrderLinkProvider` make no API calls. Shared hooks key their effects on primitives (`useExports`, `useBranchMedia`, `usePosBranch`, `useOrderQueue`, `useOrderDetail`), and `useCan` and `useMenuFilters` do no I/O. No refetch loops were found, and every interval is cleared on cleanup. A token refresh does not trigger a fetch storm. The backend sets `X-Access-Token` only when scopes change (`liveAccess.js:105-117`), and the cost is extra re-renders, not refetches. Several in-flight responses can each dispatch `TOKEN_REFRESHED_EVENT` (suspected, low). `switchTenant` reloads the page by design. The `/api/exports` catalogue is promise-cached (`services/exportService.js:36-55`) and costs no queries on the server. There is no per-page `/me` call. `CustomerPicker` search, Dues search, Dine quote (300 ms with sequence guards) and the ExportDialog preview (300 ms) are all debounced. Finance, Returns, CashSessions, PaymentMethods, DailyStock, PortalMenu and QrCodes each fetch once per load or filter change. Tokens (15 s), TokenDisplay (5 s, a public display), online orders (10 s) and Dine status each poll once, with no duplicate poller. On the backend, list reads are batched: pricing uses one IN query, availability and stock take one read per page, `loadDishes` runs 9 queries on one connection, and menu options run 12 on one connection. One more defect was found that is not a duplicate: Floor › Tables calls `getFloors()`/`getTables()` with no limit and so gets only the API default of 10 rows (`Tables.js:33-55`).

## Conclusion

The lesson is that "duplicate calls on page load" is mostly the wrong framing for this app. First paint is fairly clean. The cost comes from **actions and timers that re-run whole loads** on long-lived screens, and from a backend that charges an audit write and possibly three auth queries for every read. That means the highest-leverage fixes are on the server, not in individual components. Skipping audit rows for GETs (or at least for DEBUG-level ones), memoising `liveAccess` loads in flight, and passing one connection through the pricing and overview fan-outs would cut the cost of every remaining duplicate at once. On the client, three changes cover most of the traffic: debounce the till quote and the Ledger search, make post-action reloads targeted, and add a small session promise cache for branches and other static lookups like the one exports already has.

Two numbers are still unknown and should be measured before prioritising: how often `liveAccess` actually misses on Vercel, and how expensive the pending-QR and dues queries are. Both would change the ranking of cases 3 and 6.
